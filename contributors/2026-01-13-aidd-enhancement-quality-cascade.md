# Enhancement: Quality Cascade v2

**Дата**: 2026-01-13
**Автор**: AI Agent
**Статус**: Proposal
**Контекст**: Анализ F005-C выявил системную проблему в процессе

---

## 1. Проблема

### 1.1 Симптом

На этапе `/research` для F005-C была предложена структура из 5 файлов с нарушениями DRY/KISS/YAGNI. Ошибка прошла бы через весь пайплайн до Review.

### 1.2 Корневая причина

```
/idea → /research → /plan → /generate → /review
  ❌       ❌         ❌        ❌          ✅

Принципы качества проверяются ТОЛЬКО на этапе Review.
```

---

## 2. Решение: Quality Cascade v2

### 2.1 Ключевой принцип

**Каждая роль проверяет ВСЕ применимые принципы. Все проверки ОБЯЗАТЕЛЬНЫ.**

```
Ошибка → [Research]  → [Architect]  → [Implement]  → [Review]
          7 проверок   16 проверок   17 проверок   17 проверок
          ОБЯЗАТЕЛЬНО  ОБЯЗАТЕЛЬНО   ОБЯЗАТЕЛЬНО   ОБЯЗАТЕЛЬНО
```

### 2.2 Применимость принципов

| Принцип | Research | Architect | Implement | Review |
|---------|:--------:|:---------:|:---------:|:------:|
| DRY | ✓ | ✓ | ✓ | ✓ |
| KISS | ✓ | ✓ | ✓ | ✓ |
| YAGNI | ✓ | ✓ | ✓ | ✓ |
| SRP | - | ✓ | ✓ | ✓ |
| OCP | - | ✓ | ✓ | ✓ |
| LSP | - | - | ✓ | ✓ |
| ISP | - | ✓ | ✓ | ✓ |
| DIP | - | ✓ | ✓ | ✓ |
| SoC | ✓ | ✓ | ✓ | ✓ |
| SSoT | ✓ | ✓ | ✓ | ✓ |
| LoD | - | ✓ | ✓ | ✓ |
| CoC | ✓ | ✓ | ✓ | ✓ |
| Fail Fast | - | ✓ | ✓ | ✓ |
| Explicit | - | ✓ | ✓ | ✓ |
| Composition | - | ✓ | ✓ | ✓ |
| Testability | - | ✓ | ✓ | ✓ |
| Security | ✓ | ✓ | ✓ | ✓ |
| **Итого** | **7** | **16** | **17** | **17** |

**Легенда:**
- ✓ = ОБЯЗАТЕЛЬНАЯ проверка
- `-` = Неприменимо (нет артефакта для проверки)

## 3. Researcher: 7 обязательных проверок

**Артефакт**: Research Report (анализ существующего кода)

---

### 3.1 DRY (Don't Repeat Yourself)

**Цель для Researcher**: Выявить существующий код для переиспользования и предотвратить создание дублей на этапе планирования.

**Обязательный чеклист**:
- [ ] Выполнен поиск похожих модулей (`grep`, `find`, анализ структуры)
- [ ] Найденные утилиты и хелперы задокументированы
- [ ] Существующие конфигурации выявлены (settings.py, config и т.д.)
- [ ] Предложения из PRD проверены на дублирование с существующим кодом
- [ ] В отчёте есть секция "Код для переиспользования"

**Критерий выполнения**: Research Report содержит явный список существующих модулей с рекомендацией "использовать" или "расширить" вместо "создать новый".

---

### 3.2 KISS (Keep It Simple, Stupid)

**Цель для Researcher**: Критически оценить сложность предложений в PRD и выявить возможности упрощения.

**Обязательный чеклист**:
- [ ] Каждый предлагаемый компонент из PRD оценён на необходимость
- [ ] Сложные решения отмечены с вопросом "можно ли проще?"
- [ ] Выявлены паттерны упрощения в существующем коде
- [ ] Предложены альтернативы для сложных компонентов
- [ ] В отчёте есть секция "Анализ сложности PRD"

**Критерий выполнения**: Research Report содержит критический анализ каждого компонента PRD с оценкой сложности.

---

### 3.3 YAGNI (You Aren't Gonna Need It)

**Цель для Researcher**: Отфильтровать компоненты "на будущее" и ограничить scope текущими требованиями.

**Обязательный чеклист**:
- [ ] Каждый компонент PRD проверен: "нужен ли сейчас?"
- [ ] Компоненты "на будущее" явно отмечены
- [ ] Scope ограничен минимально необходимым
- [ ] Рекомендации по исключению избыточного функционала даны
- [ ] В отчёте есть секция "Фильтрация scope"

**Критерий выполнения**: Research Report содержит явный список "исключить из текущей итерации" с обоснованием.

---

### 3.4 SoC (Separation of Concerns)

**Цель для Researcher**: Проанализировать разделение ответственностей в существующем коде для правильной интеграции.

**Обязательный чеклист**:
- [ ] Структура существующих модулей проанализирована
- [ ] Ответственности каждого модуля задокументированы
- [ ] Границы между модулями определены
- [ ] Точки интеграции для новой функциональности выявлены
- [ ] В отчёте есть секция "Архитектура существующего кода"

**Критерий выполнения**: Research Report содержит диаграмму или описание ответственностей существующих модулей.

---

### 3.5 SSoT (Single Source of Truth)

**Цель для Researcher**: Определить где хранятся данные, конфигурации и типы, чтобы не создавать дубли.

**Обязательный чеклист**:
- [ ] Файлы конфигурации найдены и задокументированы
- [ ] Места определения типов/моделей выявлены
- [ ] Константы и их расположение описаны
- [ ] Рекомендации по использованию существующих источников даны
- [ ] В отчёте есть секция "Источники данных"

**Критерий выполнения**: Research Report содержит таблицу "Тип данных → Файл-источник".

---

### 3.6 CoC (Convention over Configuration)

**Цель для Researcher**: Выявить существующие конвенции проекта для их соблюдения.

**Обязательный чеклист**:
- [ ] Стиль кода проанализирован (именование, структура)
- [ ] Паттерны проекта задокументированы
- [ ] Существующие соглашения выявлены
- [ ] Рекомендации по следованию конвенциям даны
- [ ] В отчёте есть секция "Конвенции проекта"

**Критерий выполнения**: Research Report содержит список конвенций с примерами из кода.

---

### 3.7 Security

**Цель для Researcher**: Проанализировать существующие практики безопасности для их соблюдения.

**Обязательный чеклист**:
- [ ] Существующие механизмы валидации выявлены
- [ ] Паттерны обработки sensitive данных задокументированы
- [ ] Практики авторизации/аутентификации описаны
- [ ] Потенциальные security-риски новой функциональности отмечены
- [ ] В отчёте есть секция "Security-контекст"

**Критерий выполнения**: Research Report содержит описание security-паттернов проекта.

## 4. Architect: 16 обязательных проверок

**Артефакт**: Architecture Plan (план реализации)

---

### 4.1 DRY (Don't Repeat Yourself)

**Цель для Architect**: Убедиться что план не создаёт дублирования с существующим кодом или внутри себя.

**Обязательный чеклист**:
- [ ] План сверен с Research Report (секция "Код для переиспользования")
- [ ] Новые компоненты не дублируют существующие
- [ ] Внутри плана нет дублирования между компонентами
- [ ] Общая логика вынесена в переиспользуемые модули
- [ ] В плане есть секция "Переиспользование"

**Критерий выполнения**: План явно указывает какой существующий код используется и почему не создаются дубли.

---

### 4.2 KISS (Keep It Simple, Stupid)

**Цель для Architect**: Создать минимально сложную архитектуру, достаточную для требований.

**Обязательный чеклист**:
- [ ] Количество новых файлов минимизировано
- [ ] Иерархия зависимостей простая (нет циклов, минимум уровней)
- [ ] Нет преждевременных абстракций
- [ ] Каждый компонент обоснован
- [ ] В плане есть секция "Обоснование структуры"

**Критерий выполнения**: План содержит ответ на вопрос "почему нельзя проще?" для каждого компонента.

---

### 4.3 YAGNI (You Aren't Gonna Need It)

**Цель для Architect**: Включить в план только компоненты, необходимые для текущих требований.

**Обязательный чеклист**:
- [ ] Каждый компонент привязан к конкретному требованию из PRD
- [ ] Нет компонентов "для расширяемости"
- [ ] Интерфейсы минимальны (только нужные методы)
- [ ] Нет абстракций без текущего использования
- [ ] В плане есть секция "Трассировка требований"

**Критерий выполнения**: План содержит таблицу "Компонент → Требование PRD".

---

### 4.4 SRP (Single Responsibility Principle)

**Цель для Architect**: Каждый модуль в плане должен иметь одну чётко определённую ответственность.

**Обязательный чеклист**:
- [ ] Для каждого модуля определена единственная ответственность
- [ ] Ответственности не пересекаются между модулями
- [ ] Нет God-модулей (делающих всё)
- [ ] Изменение требования затрагивает минимум модулей
- [ ] В плане есть секция "Ответственности модулей"

**Критерий выполнения**: План содержит таблицу "Модуль → Единственная ответственность".

---

### 4.5 OCP (Open/Closed Principle)

**Цель для Architect**: Архитектура позволяет расширение без модификации существующего кода.

**Обязательный чеклист**:
- [ ] Точки расширения определены
- [ ] Новая функциональность добавляется без изменения существующего
- [ ] Используются абстракции для вариативности
- [ ] Breaking changes минимизированы
- [ ] В плане есть секция "Точки расширения"

**Критерий выполнения**: План показывает как добавить похожую функциональность без модификации.

---

### 4.6 ISP (Interface Segregation Principle)

**Цель для Architect**: Интерфейсы маленькие и специфичные, клиенты не зависят от ненужных методов.

**Обязательный чеклист**:
- [ ] Интерфейсы содержат только необходимые методы
- [ ] Большие интерфейсы разбиты на специфичные
- [ ] Клиенты зависят только от используемых методов
- [ ] Нет "толстых" интерфейсов
- [ ] В плане есть секция "Контракты/Интерфейсы"

**Критерий выполнения**: План содержит описание интерфейсов с обоснованием их минимальности.

---

### 4.7 DIP (Dependency Inversion Principle)

**Цель для Architect**: Высокоуровневые модули не зависят от низкоуровневых, оба зависят от абстракций.

**Обязательный чеклист**:
- [ ] Зависимости направлены к абстракциям
- [ ] Высокоуровневая логика не зависит от деталей реализации
- [ ] Инверсия зависимостей применена где необходимо
- [ ] Конкретные реализации заменяемы
- [ ] В плане есть секция "Граф зависимостей"

**Критерий выполнения**: План содержит диаграмму зависимостей с указанием абстракций.

---

### 4.8 SoC (Separation of Concerns)

**Цель для Architect**: Чёткое разделение ответственностей между слоями и модулями.

**Обязательный чеклист**:
- [ ] Слои архитектуры чётко определены
- [ ] Бизнес-логика отделена от инфраструктуры
- [ ] Представление отделено от данных
- [ ] Границы между модулями явные
- [ ] В плане есть секция "Слои архитектуры"

**Критерий выполнения**: План содержит описание слоёв с правилами взаимодействия.

---

### 4.9 SSoT (Single Source of Truth)

**Цель для Architect**: Каждый тип данных определён в одном месте.

**Обязательный чеклист**:
- [ ] Конфигурация в одном файле (settings.py)
- [ ] Типы/модели определены единожды
- [ ] Константы не дублируются
- [ ] Новые данные добавляются в существующие источники
- [ ] В плане есть секция "Источники данных"

**Критерий выполнения**: План явно указывает где определяются новые типы и почему именно там.

---

### 4.10 LoD (Law of Demeter)

**Цель для Architect**: Минимизировать связанность между модулями.

**Обязательный чеклист**:
- [ ] Модули взаимодействуют через чёткие API
- [ ] Модули не знают внутренности других модулей
- [ ] Цепочки вызовов минимизированы (a.b.c.d → плохо)
- [ ] Зависимости явные и минимальные
- [ ] В плане есть секция "Связанность модулей"

**Критерий выполнения**: План показывает какие модули с какими взаимодействуют и как.

---

### 4.11 CoC (Convention over Configuration)

**Цель для Architect**: Следовать существующим конвенциям проекта.

**Обязательный чеклист**:
- [ ] Именование следует паттернам проекта
- [ ] Структура файлов соответствует существующей
- [ ] Новые правила минимизированы
- [ ] Конвенции из Research Report учтены
- [ ] В плане есть секция "Соответствие конвенциям"

**Критерий выполнения**: План явно указывает какие конвенции применяются.

---

### 4.12 Fail Fast

**Цель для Architect**: Определить стратегию обработки ошибок на уровне архитектуры.

**Обязательный чеклист**:
- [ ] Стратегия валидации входных данных определена
- [ ] Точки валидации указаны (границы системы)
- [ ] Типы ошибок и их обработка описаны
- [ ] Принцип "падать рано и явно" заложен
- [ ] В плане есть секция "Обработка ошибок"

**Критерий выполнения**: План содержит описание где и как происходит валидация.

---

### 4.13 Explicit > Implicit

**Цель для Architect**: Контракты и зависимости явные, нет скрытого поведения.

**Обязательный чеклист**:
- [ ] API контракты явно описаны
- [ ] Зависимости явно указаны
- [ ] Нет магического поведения
- [ ] Побочные эффекты задокументированы
- [ ] В плане есть секция "API контракты"

**Критерий выполнения**: План содержит явные сигнатуры ключевых функций.

---

### 4.14 Composition > Inheritance

**Цель для Architect**: Предпочитать композицию наследованию.

**Обязательный чеклист**:
- [ ] Иерархии наследования минимальны (≤ 2-3 уровня)
- [ ] Композиция используется для переиспользования
- [ ] Mixins вместо множественного наследования
- [ ] Обоснование если используется наследование
- [ ] В плане есть секция "Паттерны переиспользования"

**Критерий выполнения**: План показывает как достигается переиспользование кода.

---

### 4.15 Testability

**Цель для Architect**: Архитектура позволяет написать unit-тесты для каждого компонента.

**Обязательный чеклист**:
- [ ] Компоненты можно тестировать изолированно
- [ ] Зависимости можно подменить (mock/stub)
- [ ] Нет скрытых зависимостей от глобального состояния
- [ ] Стратегия тестирования определена
- [ ] В плане есть секция "Тестируемость"

**Критерий выполнения**: План показывает как тестировать каждый компонент.

---

### 4.16 Security

**Цель для Architect**: Заложить безопасность на уровне архитектуры.

**Обязательный чеклист**:
- [ ] Границы доверия определены
- [ ] Точки валидации входных данных указаны
- [ ] Принцип минимальных привилегий применён
- [ ] Sensitive данные защищены
- [ ] В плане есть секция "Security-архитектура"

**Критерий выполнения**: План содержит описание security-мер.

---

## 5. Implementer: 17 обязательных проверок

**Артефакт**: Код

---

### 5.1 DRY (Don't Repeat Yourself)

**Цель для Implementer**: Не писать код который уже существует или который дублируется внутри реализации.

**Обязательный чеклист**:
- [ ] Перед написанием нового кода проверен существующий
- [ ] Общая логика вынесена в функции/методы
- [ ] Нет copy-paste между файлами
- [ ] Нет copy-paste внутри файла
- [ ] Используются существующие утилиты из Research Report

**Критерий выполнения**: Нет дублирующегося кода (проверяемо через code review).

---

### 5.2 KISS (Keep It Simple, Stupid)

**Цель для Implementer**: Писать простой, читаемый код без over-engineering.

**Обязательный чеклист**:
- [ ] Простые решения предпочтены умным
- [ ] Читаемость важнее краткости
- [ ] Нет преждевременной оптимизации
- [ ] Нет избыточных абстракций
- [ ] Код понятен без длинных объяснений

**Критерий выполнения**: Код можно понять за один проход чтения.

---

### 5.3 YAGNI (You Aren't Gonna Need It)

**Цель для Implementer**: Реализовать только то что указано в плане, не добавлять "на будущее".

**Обязательный чеклист**:
- [ ] Реализовано только то что в плане
- [ ] Нет методов "про запас"
- [ ] Нет параметров "на будущее"
- [ ] Нет закомментированного кода для будущего
- [ ] Каждая строка кода обоснована требованием

**Критерий выполнения**: Весь код привязан к конкретному требованию.

---

### 5.4 SRP (Single Responsibility Principle)

**Цель для Implementer**: Каждая функция/класс делает одну вещь.

**Обязательный чеклист**:
- [ ] Каждая функция имеет одну задачу
- [ ] Каждый класс имеет одну ответственность
- [ ] Функции < 50 строк (или обоснование)
- [ ] Имя функции полностью описывает что она делает
- [ ] Нет функций с "and" в названии (do_x_and_y)

**Критерий выполнения**: Можно описать функцию одним предложением без "и".

---

### 5.5 OCP (Open/Closed Principle)

**Цель для Implementer**: Реализовать код который можно расширить без модификации.

**Обязательный чеклист**:
- [ ] Используются абстракции для вариативности
- [ ] Новые варианты добавляются без изменения существующего
- [ ] Полиморфизм вместо условных операторов (где уместно)
- [ ] Точки расширения из плана реализованы
- [ ] Существующий код не модифицирован (только расширен)

**Критерий выполнения**: Можно добавить новый вариант поведения без изменения существующего кода.

---

### 5.6 LSP (Liskov Substitution Principle)

**Цель для Implementer**: Подтипы полностью заменяют родительские типы.

**Обязательный чеклист**:
- [ ] Подклассы не меняют поведение родителя
- [ ] Контракты родителя соблюдаются
- [ ] Нет исключений в переопределённых методах которых нет в родителе
- [ ] Предусловия не усилены
- [ ] Постусловия не ослаблены

**Критерий выполнения**: Код работает корректно при замене родителя на любой подтип.

---

### 5.7 ISP (Interface Segregation Principle)

**Цель для Implementer**: Реализовать маленькие, специфичные интерфейсы.

**Обязательный чеклист**:
- [ ] Интерфейсы/протоколы минимальны
- [ ] Клиенты не зависят от методов которые не используют
- [ ] Большие интерфейсы разбиты
- [ ] Нет пустых реализаций методов (NotImplemented)
- [ ] Каждый метод интерфейса используется

**Критерий выполнения**: Нет методов которые реализованы но не используются.

---

### 5.8 DIP (Dependency Inversion Principle)

**Цель для Implementer**: Зависеть от абстракций, не от конкретных реализаций.

**Обязательный чеклист**:
- [ ] Зависимости инжектируются через параметры
- [ ] Используются интерфейсы/протоколы для зависимостей
- [ ] Высокоуровневый код не импортирует низкоуровневый напрямую
- [ ] Конкретные реализации заменяемы
- [ ] Нет hardcoded зависимостей от конкретных классов

**Критерий выполнения**: Можно заменить любую зависимость без изменения кода.

---

### 5.9 SoC (Separation of Concerns)

**Цель для Implementer**: Разделить код по ответственностям.

**Обязательный чеклист**:
- [ ] Бизнес-логика отделена от I/O
- [ ] Валидация отделена от обработки
- [ ] Форматирование отделено от логики
- [ ] Каждый файл имеет одну тему
- [ ] Функции не смешивают разные уровни абстракции

**Критерий выполнения**: Каждая функция работает на одном уровне абстракции.

---

### 5.10 SSoT (Single Source of Truth)

**Цель для Implementer**: Использовать существующие источники данных, не создавать дубли.

**Обязательный чеклист**:
- [ ] Конфигурация берётся из settings.py
- [ ] Типы импортируются из существующих модулей
- [ ] Константы не дублируются
- [ ] Нет локальных копий данных из других модулей
- [ ] Используется SSoT из плана архитектуры

**Критерий выполнения**: Каждый тип данных определён в одном месте.

---

### 5.11 LoD (Law of Demeter)

**Цель для Implementer**: Минимизировать связанность, не лезть во внутренности других объектов.

**Обязательный чеклист**:
- [ ] Нет цепочек вызовов (a.b.c.d)
- [ ] Объекты взаимодействуют только с непосредственными зависимостями
- [ ] Нет доступа к внутренним структурам других объектов
- [ ] Используются фасады/обёртки где нужно
- [ ] Минимум импортов в каждом файле

**Критерий выполнения**: Каждая функция знает только о своих прямых зависимостях.

---

### 5.12 CoC (Convention over Configuration)

**Цель для Implementer**: Следовать конвенциям проекта.

**Обязательный чеклист**:
- [ ] Именование соответствует стилю проекта
- [ ] Структура файла соответствует существующим
- [ ] Используются существующие паттерны
- [ ] Новые конвенции не вводятся без необходимости
- [ ] Code style соответствует проекту (linter проходит)

**Критерий выполнения**: Код неотличим по стилю от существующего.

---

### 5.13 Fail Fast

**Цель для Implementer**: Валидировать рано, падать явно.

**Обязательный чеклист**:
- [ ] Входные данные валидируются в начале функции
- [ ] Guard clauses вместо глубокой вложенности
- [ ] Явные исключения вместо тихих ошибок
- [ ] Нет проглатывания исключений (except: pass)
- [ ] Ошибки информативны (сообщение объясняет проблему)

**Критерий выполнения**: При некорректных данных код падает сразу с понятным сообщением.

---

### 5.14 Explicit > Implicit

**Цель для Implementer**: Писать явный код без магии.

**Обязательный чеклист**:
- [ ] Параметры явные (нет *args/**kwargs без необходимости)
- [ ] Нет магических чисел (используются константы)
- [ ] Type hints для публичных функций
- [ ] Нет скрытых побочных эффектов
- [ ] Поведение очевидно из кода

**Критерий выполнения**: Можно понять что делает код без изучения контекста.

---

### 5.15 Composition > Inheritance

**Цель для Implementer**: Предпочитать композицию наследованию.

**Обязательный чеклист**:
- [ ] Наследование используется только для is-a отношений
- [ ] Глубина наследования ≤ 2-3
- [ ] Композиция для переиспользования логики
- [ ] Нет множественного наследования (кроме mixins)
- [ ] Если наследование — обосновано

**Критерий выполнения**: Каждое использование наследования обосновано.

---

### 5.16 Testability

**Цель для Implementer**: Писать код который можно протестировать.

**Обязательный чеклист**:
- [ ] Функции детерминированы (один вход → один выход)
- [ ] Зависимости инжектируются
- [ ] Нет глобального состояния
- [ ] Побочные эффекты изолированы
- [ ] Можно написать unit-тест без сложного setup

**Критерий выполнения**: Unit-тест для функции умещается в 10-15 строк.

---

### 5.17 Security

**Цель для Implementer**: Писать безопасный код.

**Обязательный чеклист**:
- [ ] Входные данные валидируются и санитизируются
- [ ] Нет SQL/XSS/Command injection
- [ ] Secrets не хардкодятся
- [ ] Минимальные привилегии
- [ ] Sensitive данные не логируются

**Критерий выполнения**: Код проходит security checklist.

---

## 6. Reviewer: 17 обязательных проверок

**Артефакт**: Код + все предыдущие артефакты

---

### 6.1 DRY (Don't Repeat Yourself)

**Цель для Reviewer**: Убедиться что нет дублирования кода.

**Обязательный чеклист**:
- [ ] Проверен каждый новый файл на дублирование с существующим кодом
- [ ] Проверено внутреннее дублирование (внутри файла)
- [ ] Проверено дублирование между новыми файлами
- [ ] Похожие блоки кода выявлены
- [ ] Рекомендации по устранению дублирования даны

**Критерий выполнения**: Явное подтверждение "дублирование не обнаружено" или список найденного.

---

### 6.2 KISS (Keep It Simple, Stupid)

**Цель для Reviewer**: Убедиться что код максимально прост.

**Обязательный чеклист**:
- [ ] Сложные функции выявлены (> 50 строк)
- [ ] Глубокая вложенность выявлена (> 4 уровней)
- [ ] Over-engineering выявлен
- [ ] Альтернативные простые решения предложены
- [ ] Цикломатическая сложность проверена (< 10)

**Критерий выполнения**: Метрики сложности в норме или обоснованы.

---

### 6.3 YAGNI (You Aren't Gonna Need It)

**Цель для Reviewer**: Убедиться что реализовано только необходимое.

**Обязательный чеклист**:
- [ ] Каждая функция привязана к требованию
- [ ] Нет неиспользуемого кода
- [ ] Нет методов "про запас"
- [ ] Нет избыточных параметров
- [ ] Код соответствует плану (не больше)

**Критерий выполнения**: Весь код трассируется к требованиям PRD.

---

### 6.4 SRP (Single Responsibility Principle)

**Цель для Reviewer**: Убедиться что каждый компонент имеет одну ответственность.

**Обязательный чеклист**:
- [ ] Каждая функция делает одну вещь
- [ ] Каждый класс имеет одну ответственность
- [ ] Файлы не перегружены (< 500 строк)
- [ ] Нет God-объектов
- [ ] Имена соответствуют ответственности

**Критерий выполнения**: Каждый компонент описывается одним предложением.

---

### 6.5 OCP (Open/Closed Principle)

**Цель для Reviewer**: Убедиться что код расширяем без модификации.

**Обязательный чеклист**:
- [ ] Точки расширения из плана реализованы
- [ ] Существующий код не сломан
- [ ] Абстракции используются корректно
- [ ] Можно добавить новый вариант без изменений
- [ ] Breaking changes отсутствуют

**Критерий выполнения**: Существующие тесты проходят без изменений.

---

### 6.6 LSP (Liskov Substitution Principle)

**Цель для Reviewer**: Убедиться что подтипы корректно заменяют родителей.

**Обязательный чеклист**:
- [ ] Контракты родителей соблюдены
- [ ] Поведение подтипов совместимо
- [ ] Нет неожиданных исключений
- [ ] Инварианты сохранены
- [ ] Тесты родителей проходят для подтипов

**Критерий выполнения**: Подтипы можно использовать везде где ожидается родитель.

---

### 6.7 ISP (Interface Segregation Principle)

**Цель для Reviewer**: Убедиться что интерфейсы минимальны.

**Обязательный чеклист**:
- [ ] Нет толстых интерфейсов
- [ ] Все методы интерфейса используются
- [ ] Нет NotImplemented заглушек
- [ ] Клиенты не зависят от лишнего
- [ ] Интерфейсы специфичны

**Критерий выполнения**: Каждый метод интерфейса имеет клиента.

---

### 6.8 DIP (Dependency Inversion Principle)

**Цель для Reviewer**: Убедиться что зависимости правильно организованы.

**Обязательный чеклист**:
- [ ] Зависимости инжектируются
- [ ] Нет hardcoded зависимостей
- [ ] Используются абстракции
- [ ] Граф зависимостей соответствует плану
- [ ] Можно подменить зависимости для тестов

**Критерий выполнения**: Все зависимости mockable.

---

### 6.9 SoC (Separation of Concerns)

**Цель для Reviewer**: Убедиться в правильном разделении ответственностей.

**Обязательный чеклист**:
- [ ] Слои не смешаны
- [ ] Бизнес-логика изолирована
- [ ] I/O изолирован
- [ ] Уровни абстракции не смешаны
- [ ] Границы модулей чёткие

**Критерий выполнения**: Каждый слой можно изменить независимо.

---

### 6.10 SSoT (Single Source of Truth)

**Цель для Reviewer**: Убедиться что данные не дублируются.

**Обязательный чеклист**:
- [ ] Конфигурация из settings.py
- [ ] Типы из одного места
- [ ] Константы не дублируются
- [ ] Нет локальных копий данных
- [ ] SSoT из плана соблюдён

**Критерий выполнения**: Каждый тип данных определён в одном месте.

---

### 6.11 LoD (Law of Demeter)

**Цель для Reviewer**: Убедиться в низкой связанности.

**Обязательный чеклист**:
- [ ] Нет длинных цепочек вызовов
- [ ] Модули не знают внутренности других
- [ ] Зависимости минимальны
- [ ] API чёткие
- [ ] Импорты минимальны

**Критерий выполнения**: Изменение внутренностей модуля не ломает другие.

---

### 6.12 CoC (Convention over Configuration)

**Цель для Reviewer**: Убедиться в соблюдении конвенций.

**Обязательный чеклист**:
- [ ] Стиль кода соответствует проекту
- [ ] Linter проходит
- [ ] Именование консистентно
- [ ] Структура стандартная
- [ ] Документация в формате проекта

**Критерий выполнения**: Код неотличим от существующего по стилю.

---

### 6.13 Fail Fast

**Цель для Reviewer**: Убедиться в правильной обработке ошибок.

**Обязательный чеклист**:
- [ ] Валидация на входе
- [ ] Явные исключения
- [ ] Информативные сообщения
- [ ] Нет проглатывания ошибок
- [ ] Guard clauses используются

**Критерий выполнения**: Ошибки обнаруживаются рано и понятно.

---

### 6.14 Explicit > Implicit

**Цель для Reviewer**: Убедиться в явности кода.

**Обязательный чеклист**:
- [ ] Type hints присутствуют
- [ ] Нет магических чисел
- [ ] Поведение очевидно
- [ ] Побочные эффекты задокументированы
- [ ] API явные

**Критерий выполнения**: Код понятен без дополнительного контекста.

---

### 6.15 Composition > Inheritance

**Цель для Reviewer**: Убедиться в правильном использовании наследования.

**Обязательный чеклист**:
- [ ] Наследование обосновано
- [ ] Глубина минимальна
- [ ] Композиция где возможно
- [ ] Нет diamond problem
- [ ] Mixins корректны

**Критерий выполнения**: Каждое наследование имеет обоснование.

---

### 6.16 Testability

**Цель для Reviewer**: Убедиться что код тестируем.

**Обязательный чеклист**:
- [ ] Unit-тесты написаны
- [ ] Покрытие достаточное
- [ ] Тесты изолированы
- [ ] Моки минимальны
- [ ] Тесты понятны

**Критерий выполнения**: Каждый публичный метод имеет тест.

**Обязательный чеклист**:

- [ ] Sensitive данные защищены
